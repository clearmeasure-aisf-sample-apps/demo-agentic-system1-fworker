Reviewed 2026-10-11 (`pr-qc-environment-review.md`, 18 findings and the listed gaps applied). ## 0. Summary

For a pull request whose work item does NOT carry `Auto Merge`, a person does quality control on a running copy of the change. The gateway comments a link on the PR and on the work item that OFFERS an environment. Nothing starts until a person clicks Start (the link, or the dashboard button). Then the plant manager assigns a `qc-env` job to one connected worker session. That session fetches the PR head, builds and runs the app on its own computer, and reports a URL through a script verb. The person opens the URL, tests, and approves the PR on GitHub. The gateway tears the environment down when the PR merges or closes, or at the lifetime or idle cap.

Three decisions carry the design (decided 2026-10-11, section 10):

1. Anyone can click. The link carries no identity check. It is a signed, expiring, single-purpose token bound to PR number and head SHA; GET has no side effect. Reachability is by network: the environment runs on the worker's own computer, never Azure, so the URL works only for people who can reach that computer (same subnet, same tailnet or VPN). Only a GitHub review by a person in `humanApprovers` counts toward merge.
2. The sandbox is whatever environment the session runs in. Each session carries a "QC environment profile" in its connect prompt that says how that machine builds and runs the app. The PR text is data; the profile is written by the operator.
3. A QC environment starts only on a person's request. The sweep never creates or assigns a QC job and never rebuilds on a new head. Automatic teardown stays because it only stops things.

The QC state transitions are persisted in the work item's state comment (`qc` section, one record per PR, created at Start), written only by gateway verbs. Lease, heartbeat, URL, client address, probe results and log tail live in gateway memory only (3.1). The worker moves the record only through item-scoped `qc` role verbs.

## 1. User flow

| # | Step | Actor | Result |
|---|---|---|---|
| 1 | Item reaches Functional Testing with a recorded PASS verdict, a PR open, no `Auto Merge` label, not docs-only | sweep (`qc-sync`) | PR is `available` (derived state, no QC record, no job) |
| 2 | Comment on the PR and on the work item (one each, edited in place afterwards) | gateway | Offers an environment: link plus the head SHA it is for |
| 3 | Person clicks the link in a browser | person | Confirmation page: PR, title, head SHA, author, what will happen ("run this branch on <worker>'s computer; reachable only from networks that can reach that computer"), button "Start QC environment" |
| 4 | Person presses Start (or the dashboard Start button) | person | `POST /qc/{pr}/start`: QC record created `requested`, plant manager picks a worker, state `assigned` |
| 5 | Page polls `GET /qc/{pr}/status` every 3 s: state line, worker name, elapsed time, last build log lines (redacted) | page | "assigned", "building", "starting", "ready" |
| 6 | Worker builds, runs, checks health locally, reports `ready` with URL; gateway probe is best-effort (section 4.3 step 8) | worker, gateway | Page shows "Open the environment" (the URL) and the reachability notice |
| 7 | Person tests, then approves on GitHub: review "Approve" on the PR (own account, listed in `humanApprovers`) | person | `pull_request_review` webhook; the approval counts at the current head (section 3.6) |
| 8 | Reset: button on the QC page or the dashboard: rebuild at the current head, new port, new URL, fresh data. Also the recovery after a failure | person | state `reset` then `building` |
| 9 | Teardown: automatic (merged, closed, lifetime cap, idle, head changed and no reset in 30 min) or button "Tear down" | gateway, person | Worker stops the app and removes the checkout; state `torn-down` |

Comment text (PR and item), stable marker for in-place edit:

```
QC environment available for PR #412 at head 9fd3c1a: [Start the QC environment](https://gw.example:7443/qc/412?t=q1....)
Nothing runs until someone presses Start. The environment runs on a factory worker's own computer and is reachable only from networks that can reach that computer (<worker name> is chosen at Start).
The link works for 7 days and only for this commit.
<!-- qc link pr=412 -->
```

A new head edits the same comment with a new link and the new SHA (the old link is then stale, section 2.4). It does not start anything. The text is generated by the gateway; the worker never writes it. After Start, the comment is edited once to the worker name and the page link.

## 2. Click link security

### 2.1 Token
`q1.<payload>.<hmac>`, a sibling of the existing `i1.` token. Payload (base64url JSON): `{pr, sha (full), u:"qc-open", x:expiry, n:nonce, i:item}`. The MAC is `HMAC-SHA256(FACTORY_TOKEN_SECRET, "qc:" + payload)`; the `qc:` prefix keeps it from validating as any other token. Compared in constant time (`Auth.Same`). Default expiry 7 days (`timing.qcLinkDays`). The token carries no identity. It is the capability: "this PR at this SHA may be offered for QC to whoever holds the link".

### 2.2 Who may click
Anyone who holds the link and can reach the gateway. There is no identity check, no approver list for clicking, and no operator-token fallback for the link page. The gateway address in the link comes from `FACTORY_PUBLIC_URL`; `qc-link` refuses (exit 30 `public-url-not-reachable`) only when that host is loopback or `localhost`. The record stores `requested_at`; the gateway keeps `requested_from` (client IP) in memory only. The client IP comes from ASP.NET `ForwardedHeaders` with `qc.knownProxies` as `KnownProxies` and is the right-most hop that is not a known proxy (the first hop is client-set and never trusted); `X-Forwarded-For` is ignored when `qc.trustProxy` is false. No person is recorded for a click. Dashboard Start records `requested_from: "operator"`.

Who can test is decided by the network, not the link: the URL the worker reports points at the worker's own computer, so only people who can reach that computer can open it. The QC page and the PR comment say so.

### 2.3 Replay, CSRF, rate limit
- GET has no side effect (mail scanners, chat unfurlers and browser prefetch fetch links). It renders the page and mints a `page_nonce` (distinct from the `link_nonce`, the `n` field of the token) held server-side for 10 minutes.
- `POST /qc/{pr}/start|reset|teardown` requires: the `page_nonce` (hidden field), `Origin` equal to the gateway origin, and `Content-Type: application/x-www-form-urlencoded`. A cross-site form post fails the Origin and nonce checks (CSRF). These checks protect against unintended posts; they are not identity.
- Idempotent: one live environment per PR. A second click on the same link, or by another person, while a record for that SHA is non-terminal (`requested` to `ready`, `stale`) shows the current state and starts nothing (exit 0, `outcome: "existing"`). Start on a `torn-down` or `failed` record for that SHA is a new attempt (`attempt` + 1, new assignment id), so the PR returns to available. Record creation runs under `Use-ItemLock`: two simultaneous Starts create one record. The `link_nonce` is stored in the record.
- Rate limit: 10 start/reset/teardown requests per client IP per hour and 20 per PR per hour; 429 `rate-limited` beyond that (exit 20; HTTP per the `/qc/*` table in section 6). Counters are in memory, keyed by the client IP of 2.2.

### 2.4 Stale link
Head SHA in the token differs from the PR's current head (read fresh from GitHub on POST and on GET of the page itself, never cached; the status poll answers from memory and makes no GitHub call): GET shows "this link is for an older commit" with a button "Get the current link" (the page for the current head, with a fresh token minted by the gateway), HTTP 410, reason `stale-head` (exit 11). A start request for an old SHA is never queued.

## 3. Gateway

### 3.1 QC record (in the item's state comment, key `qc`, one per PR number; exists only after Start)
```json
"qc": { "412": { "state": "ready", "sha": "9fd3c1a...", "item": 101, "author": "bot-x", "requested_at": "...", "link_nonce": "...",
  "worker": "alice-laptop", "assignment": "a-77", "attempt": 1, "port": 5410, "env_id": "qc-412-9fd3c1a-1", "probe": "verified|unverified",
  "ready_at": "...", "expires_at": "...", "fail": { "code": "build-failed", "reason": "..." },
  "approved": { "by": "jeffreypalermo", "sha": "9fd3c1a...", "at": "..." }, "history": [ {"state":"building","at":"..."} ] } }
  "approved": { "by": "jeffreypalermo", "sha": "9fd3c1a...", "at": "..." }, "history": [ {"state":"building","at":"..."} ] } }
```
Persisted only at transitions (state change, ready, fail, approval), under `Use-ItemLock`. Gateway memory only (Plant): `url`, `requested_from`, `lease_until`, `last_touch`, heartbeat values (`mem_free_mb`, `app_alive`, `local_health`), probe results, `log_tail` (1,500 characters, `Protect-JournalText`), page nonces and rate counters. `/status` and the dashboard answer from memory; heartbeats and polls cost no GitHub call. The comment is readable by anyone who can read the issue, so `url` (internal address) and client IPs never go into it. `history` is capped at 20.
`Get-State` (Board.ps1:115) parses the fence with the regex ```` (?s)```json\s*(.*?)\s*``` ```` and JSON does not escape backticks, so every worker-supplied string that is persisted (`fail.reason`, `history`) is length-capped and has backticks replaced before `Save-State`; `log_tail` is never persisted.
Gateway restart. Rebuilt from the state comments (`qc-list` over open items): state, sha, worker, assignment, attempt, env_id, port, probe, ready_at, expires_at, fail, approved. Records in `assigned` to `ready` get their Plant assignment back through `PlaceQc` as accepted by the recorded worker (same assignment id, so the worker's still valid item token keeps working); `requested` records are placed again; unacknowledged `assigned` ones are re-offered. Lost: `url`, `lease_until`, heartbeat values, `last_touch`, probe results, `log_tail`, `requested_from`, page nonces (open pages re-GET) and rate counters. Recovery: `lease_until` restarts at now + `timing.qcLeaseMinutes`, `last_touch` at the restart time (idle timer restarts), and a `ready` record without `url` shows "ready, address being re-reported". The next `qc-heartbeat` (every 60 s, sent by the worker's `watch` process, 4.3 step 9) finds no URL in memory and is answered `action: "re-report"`; `watch` then calls `qc-report` again from `E/report.json` and the record is whole. A worker that misses the grace is lost (relaunch, 3.2).

### 3.2 State machine
```
 available (derived, no record) -> [Start] -> requested -> assigned -> building -> running -> ready
                                                  |            |          |           |        |
                                                  |            +--------- failed <----+        +--> reset -> assigned -> ...
 any non-terminal -----------------------------------------------------> torn-down
```
| State | Entered by | Leaves on |
|---|---|---|
| available | sweep sees an eligible PR with no live record | Start -> requested |
| requested | Start (link or dashboard) | worker offer -> assigned; no qualifying worker: stays `requested`; `waiting` is a flag with a reason (memory), not a state; PR closed/merged -> torn-down |
| assigned | `requested` plus worker offer, or `reset` | `accept` -> building; no ack in `assignAckSeconds` -> offered to next, else back to requested |
| building | worker `qc-progress --state building` | running / failed |
| running | worker `qc-progress --state running` (process up, local health not yet seen) | `qc-report` -> ready; 3 min without local health -> failed `health-timeout` |
| ready | `qc-report` with local health ok (gateway probe verified or unverified, section 4.3 step 8) | reset, teardown, idle/lifetime expiry, app down |
| stale | head moved while the record is `assigned` to `ready` (webhook or sweep) | person presses Reset (-> `assigned`, new attempt) or `timing.qcGraceMinutes` pass -> `torn-down(head-changed)`; Start at the new head is a new record |
| failed | `qc-fail` or watchdog | person presses Reset or Start (new attempt) or teardown. Nothing resets automatically |
| reset | person | becomes assigned (same or other worker) |
| torn-down | `qc-teardown` plus worker `qc-stopped` confirmation | terminal for that SHA; the PR returns to `available` for the then-current head |

A worker lost for `leaseMinutes` (lease in memory) moves a non-terminal record to `assigned` with `mode: "relaunch"` on another worker (counts against `maxRelaunches`). This continues a person's own Start; it is not a new automatic start.
Reset, relaunch and Start on a `torn-down`/`failed` record always mint a new assignment id; the old item token (12 h today, Plant.cs:119) then fails the assignment check and dies. QC item tokens live `timing.qcTokenHours` (16; `AssignedJson` takes the TTL per kind). The config loader refuses a value not above build cap + `timing.qcLifetimeHours`, so a live environment never outlives its token; each relaunch or reset mints a fresh one.

The PR title, author and log are HTML-escaped on the QC page and the dashboard.

### 3.5 Sweep (`qc-sync`, a section of `sync-board`)
The sweep offers and tears down. It never creates a QC record, never assigns or offers a job, and never rebuilds. Per cycle, per open item with an open PR:
1. Eligibility (all must hold, else any offer is withdrawn and a `skipped` journal line written once): PR open, not draft, head repo equals base repo (`head.repo.full_name == owner/repo`), head branch matches the item's branch prefix (`factory-worker/…`), item has `column == validation` and an unprocessed PASS verdict naming this PR, item lacks `autoMergeLabel`, PR not docs-only (`docsOnlyMarker`/`docsOnlyPaths`). PRs touching the inspector's `protectedPaths` stay offered but the link page shows "needs operator confirmation"; only the dashboard (operator token) records `protected_paths_ack` (4.6).
2. No offer comment: post it (state `available`).
3. Head moved: edit the comment with the new link and SHA. Nothing is rebuilt and no job is created. A live environment for the old head is marked `stale` and torn down after `timing.qcGraceMinutes` (30) unless the person presses Reset first. Teardown is the only automatic action.
4. Automatic teardown (stops things only, never starts): `ready` with `last_touch` older than `timing.qcIdleMinutes` (120) or `ready_at` older than `timing.qcLifetimeHours` (8); PR merged/closed/item left Functional Testing (`merged`/`closed`/`left-validation`).
5. Best-effort probe of each `ready` URL every 60 s from the gateway (HTTP GET `/_healthcheck`, 5 s timeout, under the SSRF rules of 4.3 step 8; results in memory), only when `probe` is `verified` or the first probe has ever succeeded. For `unverified` records the sweep relies on the worker heartbeat (`app_alive`, `local_health`). Three consecutive probe failures of a verified URL, or `app_alive:false`: state `failed(app-down)`. No automatic reset; the QC page shows the failure and a Reset button.
6. API budget: one open-PR list call per cycle, not per record. Page polls, heartbeats, `/status` and probes make no GitHub call, so QC cannot exhaust the API quota.

### 3.6 Merge-policy interplay
The inspector runs as today; QC does not replace it and does not wait for it. The approval is unchanged: a GitHub review by a person in `humanApprovers` for the current head.

| Policy | Item without `Auto Merge` | Gate added |
|---|---|---|
| `auto` | `merge` already refuses (`no-auto-merge-label`). A person merges on GitHub, `sync-board` carries on with `settle`. QC is offered; approval is advisory | none |
| `peer-approved` | Inspector approves the head (reviewer App). A human approval from `humanApprovers` for the same head is also required. Author identity merges once both exist | new refusal in `merge`: `qc-approval-missing` (10) and `qc-not-run` (10) |

Rules for the human approval (extends `Find-HumanApproval`, which already compares `commit_id` with the head):
- Anyone may start an environment; only listed approvers' GitHub approval counts toward merge.
- Counts only if state `APPROVED` is the reviewer's latest review and `commit_id == pr.head.sha`. A new push dismisses it in effect (SHA differs); a `dismissed` review event clears `qc.approved`.
- `qc-not-run`: the approval counts for merge only if a QC environment for that SHA reached `ready` at least once (field `ready_at` set). The QC run is recorded for the PR head only (who started it is unknown by design; only client IP and time are kept). Exceptions: docs-only items; items with `Needs Human Review` hold cleared by the same person (hold clearing is unchanged: the same approval clears the inspector escalation hold and satisfies QC).
- `qc-approval-missing`: no qualifying approval at the current head.
- The approver cannot be the PR author.
- `qc.approved` (from `pr.reviewed`), and `qc.ready` when an approval for that head already exists, are routed to the owner as the trigger to retry `merge` (section 6).
- The environment is torn down once the PR is merged. It is not torn down on approval alone, but the idle timer applies.

## 4. Worker side

### 4.1 Job kind
A third job kind beside `own-item` and `bot-job`: `qc-env`. It exists only as the result of a Start. Assignment event (same shape as `item.assigned`):
```json
{ "event": "item.assigned", "item": 101, "pr": 412, "sha": "9fd3c1a...", "job": "qc-env", "role": "qc", "mode": "first|reset|relaunch",
  "assignment": "a-77", "env_id": "qc-412-9fd3c1a-1", "ackBySeconds": 30 }
```
The worker calls `factory.ps1 accept --item N --assignment a-77 --role qc` and receives a `qc` role item token for item N (Auth maps role `qc` to kind `qc-env`, not `own-item`; Plant keeps it in a separate `qcOf` map, never `ownerOf`; section 6).
`Plant.Plan` (Plant.cs:130-164) builds assignments only from the sweep's `offers` and drops unaccepted ones the sweep did not ask for, so QC assignments never go through `Plan`. A separate `Plant.PlaceQc(record)` (called by Start, reset, relaunch and the restart rebuild) creates the assignment with key `item|qc-env|qc|pr`, which `Plan`'s pruning never touches; `Tick` re-offers an unanswered one.

### 4.2 QC environment profile, capacity and selection
The sandbox is the environment the session already runs in. Each session's connect prompt (generated by the dashboard) gains an editable section "QC environment setup". The operator writes, per session, how this machine builds and runs the app, based on the architecture of the app:

| Profile field | Content |
|---|---|
| `sdk` | where the .NET SDK is (path or "on PATH") and the version |
| `database` | `sqlite` (file in `E/data/`) or a connection-string template for a local database the operator provides |
| `ports` | port range for the app (default 5400-5499) |
| `address` | how others reach this computer: `direct` (address or host name, for example the LAN or tailnet address), a tunnel command, or `none` |
| `scripts` | optional build and run commands or script paths to call instead of the defaults |
| `capacity` | QC environments at once (default 1, max 2) |

The profile is data the operator wrote for that session, not PR content. The session saves it as `qc-profile.json` in its own state directory (outside any PR checkout); `qc-local.ps1` reads it and is the only thing that runs the commands in it. PR text never supplies a command.

- A worker registers the `qc` role and the `dotnet` capability only if its profile says it can build the app. Registration: `--roles owner,inspector,qc --qc-capacity N --capabilities dotnet,git`. No profile, no `qc`. Registration also sends `qc_profile=1` and `qc_address=<host>` (`--qc-profile --qc-address HOST`; a tunnel profile declares the tunnel host suffix); the gateway keeps both in memory per worker. The dashboard worker row and the URL host check (4.3 step 8) read them; the connect prompt itself is generated in the browser and not stored.
- The profile text recommends a separate OS user for the QC session or a worker registered with `--roles qc` only. A worker registered `owner,inspector,qc` lets PR code reach an inspector item token that can `approve-pr` (4.4).
- QC jobs are counted separately from owned items (`WorkerInfo.QcCapacity`, `qcActive`): an owner session mostly waits; a QC environment holds a build and a running app (about 1.5 to 3 GB and 2 cores during build on the 4 core, 12 GB box).
- Gateway refuses to place a job when the worker's reported free memory (sent with each heartbeat: `mem_free_mb`) is below `qc.minFreeMb` (default 3500). Result: `waiting` journal, not a failure.
- Selection: workers with the `qc` role, the `dotnet` capability, free QC capacity, free memory, not draining. Prefer a worker that already holds a checkout of this PR (fast reset), then fewest active QC, then the existing type order. There is no sandbox-level criterion.
- Per PR: one live environment. Per worker: at most `qcCapacity`. Plant-wide: `qc.maxEnvironments` (default 3).

### 4.3 Skill `factory-qc-environment` (plugin/skills/factory-qc-environment/SKILL.md)
Runs in a subagent of the worker session that ends after `ready` (the main thread accepts and waits; a `qc.teardown` or `qc.reset` event wakes it to run `stop`). Steps, each a script call; the skill decides only what to do on failure.

1. `factory.ps1 accept --item N --assignment A --role qc`.
2. `factory.ps1 qc-job --item N --pr P` returns `{sha, branch, trust:{ok, reasons[]}, limits, base_dir}`. Stop on exit 10 (trust refusals, section 4.6) and report with `qc-fail`.
3. `qc-local.ps1 prepare --env-id E --sha S` (local helper, not a gateway verb): creates `base_dir/E/` outside any directory the Claude session treats as its project (default `~/.local/share/factory-worker/qc/<E>`), runs `git fetch origin pull/P/head`, verifies `FETCH_HEAD == S` (else exit 11 `stale-head`), `git worktree add`/clone, applies the checks of 4.6. Prints JSON.
4. `factory.ps1 qc-progress --item N --pr P --state building`.
5. `qc-local.ps1 build --env-id E`: the profile's build command (default `dotnet build src/UI/Server -c Release`), log to `E/build.log`, 8 minute cap. Exit 20 on timeout; 10 `build-failed` with the last 30 lines.
6. `qc-local.ps1 run --env-id E`: picks a free port in the profile's range (exit 20 `port-busy` triggers the next port, three tries), starts the app (default `dotnet run -c Release --no-build --project src/UI/Server --urls http://<bind>:<port>`) with the default environment of 4.4, detaches it with `setsid` (own process group), writes `E/app.pid`, starts `qc-local.ps1 watch` (step 9), waits up to 120 s for a local `GET /_healthcheck` 200 (the worker's own health check). `<bind>` is the profile's address; never `0.0.0.0` unless the profile says so.
7. URL choice, decided by the script from the profile, not by the model: (a) `address: direct`: `http://<address>:<port>`; (b) `address: <tunnel command>`: run it and read the URL it prints (the QC page warns that a tunnel may be public); (c) `address: none` or nothing usable: `qc-fail --code no-reachable-url`. The script validates the URL host: not loopback, not `localhost`, not `0.0.0.0`, not link-local; else exit 10 `loopback-url`.
8. `factory.ps1 qc-report --item N --pr P --sha S --env-id E --url U --port X --local-health ok`. URL rules, applied again at probe and at `/go`: scheme `http` or `https` only, no userinfo, host not loopback, `localhost`, `0.0.0.0`, link-local or metadata, and host equal to the `qc_address` the worker declared at registration (tunnel: matching the declared suffix; shown on the dashboard). The probe resolves DNS once, checks the resolved IP against the same rules (no DNS rebinding), connects to that IP and follows no redirect. It is best effort (the gateway may run in Azure and not reach the worker's network); a blind probe of a private-range address on `/_healthcheck` is accepted under the decisions. Acceptance of `ready`: (i) probe succeeds: `ready`, `probe: verified`; (ii) probe cannot connect (timeout, refused, DNS) but the worker reports `--local-health ok` and the URL passed the rules: `ready`, `probe: unverified`, and the page says the gateway could not check the address; (iii) the probe connects and answers non-200, or no local health ok: not ready (exit 20 `unreachable`, the script retries three times 10 s apart, then `qc-fail --code unreachable-url`). A person who cannot open the URL presses Reset or Tear down.
9. Heartbeat outside the model: `qc-local.ps1 watch --env-id E` (detached by `run`) calls `qc-heartbeat` every 60 s (lease, `mem_free_mb`, `app_alive`, `local_health`; held in gateway memory, nothing written to GitHub) and keeps `E/report.json`. It acts on the answer `{action:"continue"|"teardown"|"reset"|"re-report"}` itself: `re-report` calls `qc-report` again, `teardown` runs `stop` and `qc-stopped`. It also stops the app when the lease is lost, the gateway is unreachable for 15 min or the session exited, so no orphan process or port remains. The subagent never loops (token cost, Bash timeout, process reaping); the main thread's `wait-event --item N` delivers `qc.reset` and `qc.teardown`.
10. On `teardown` (run by `watch`, or by the main thread on the event): `qc-local.ps1 stop --env-id E` (kills the process tree from `app.pid`, removes `E/` including data, releases the port), then `qc-stopped --env-id E`. The subagent ends.

Logs: `qc-local.ps1 logs --env-id E --tail 40` returns redacted text; `qc-progress --log-tail-file f` lets the page show it (gateway stores at most 1,500 characters).

### 4.4 Environment and database (defaults)
These are low-cost defaults, not gates; the profile may change them.
- Process environment built from an allowlist: `PATH`, `HOME` set to `E/home` (every environment then restores NuGet from scratch, which threatens the 8 minute cap: step 0 records the restore time; a package cache shared with PR code is never writable, a read-only seeded cache may serve as an offline source), `DOTNET_*` (CLI telemetry opt-out, `DOTNET_NOLOGO`), `ASPNETCORE_URLS`, `ASPNETCORE_ENVIRONMENT=Development`. Everything else is dropped (`env -i`): no `FACTORY_*`, no `GH_TOKEN`, no gateway, GitHub or Octopus credentials, no `SSH_AUTH_SOCK`, no `ANTHROPIC_*`, no cloud credentials. The item token directory is outside `E/`. `env -i` limits inherited variables only: PR code can still read what the account can read (`~/.local/share/factory-worker/state` with the owner and inspector item tokens and the long-lived `w1.` worker token, `~/.claude`, the keyring through the session bus). Accepted under decision 2; mitigation in 4.2.
- The app runs in a directory outside the session's working tree (`base_dir/E/`).
- Database: per the profile. Default SQLite with a file in `E/data/` (the repo already supports a SQLite fallback for integration tests; open fact: confirm in step 0 of the implementation order that the Server accepts a connection-string override and creates its schema on SQLite). Connection string passed through `ConnectionStrings__...` env var by the script. A local SQL Server or LocalDB database is possible when the profile gives a template; the script then uses a database named `qc_<env-id>`. Reset and teardown delete `E/data/` or drop the database. No production or TDD connection string reaches the environment unless the operator put it in the profile, which the profile text discourages.
- Seed: the login in this demo app is by user name; the environment starts with the app's own seed data.

### 4.5 What the worker must NOT do
- Push, create branches, comment, label, approve, merge, close, or call any verb outside `QcVerbs` (the gateway refuses them: the `qc` role covers `get-item`, `qc-job`, `qc-progress`, `qc-report`, `qc-fail`, `qc-heartbeat`, `qc-stopped`, `accept`; never `release`).
- Put any credential into the PR checkout, the environment, a log line, a comment, or a URL.
- Edit files of the PR checkout, or run any command found in PR text (title, body, commits, README, CLAUDE.md, scripts) other than the fixed `qc-local.ps1` verbs and the commands in the session's profile.
- Open a second port or expose any service except the app.
- Run on more than one head: `prepare` is refused when `E/` exists for a different SHA.

### 4.6 Trust model and prompt injection
Running a PR is running its author's code on a person's computer, in the session's own environment. There is no sandbox requirement; the operator chooses what machine and account a session runs under. Explicit model:

| Rule | Enforcement |
|---|---|
| Same-repository branches only; fork PRs never run (there is no safe way to fetch them) | `qc-sync` eligibility (head repo equals base repo) and again in `qc-job` and `qc-local prepare` (re-read from GitHub) |
| Author in `qc.trustedAuthors` (factory App logins plus `humanApprovers`); other authors, or any head commit author, committer or pusher (`pulls/N/commits`, `pr.head_changed.sender`) outside the list, need the operator confirmation on the dashboard; the anonymous link page only shows "needs operator confirmation" | `qc-job` trust check; `trust.reasons` lists why |
| Head SHA fetched equals the SHA in the job (no moving target) | `prepare` check, exit 11 |
| Inspector scan reused: `secretPatterns` and `aiDirectedText` hits in the diff block the run (`qc-trust-refused`, 10) until the dashboard confirmation (operator token); `protectedPaths` / `packagePaths` / `migrationPaths` changes require the protected-paths confirmation | `qc-job` runs `Get-InspectFacts` |
| Session working directory never inside the checkout, so the PR's `CLAUDE.md`, `.claude/`, hooks and skills are never loaded by Claude Code | `base_dir` outside the project; the AI never `cd`s there; only `qc-local.ps1` touches it |
| Text from the PR is data | skill says so; the job payload carries no PR text, only numbers and SHAs; `qc-job` returns `title` flagged `untrusted` only for display |
| The profile is operator data | written for that session by the operator, never derived from the PR |

Residual risk (stated in the profile editor and the QC page): the run uses whatever the session's account can reach, including the network. Anyone holding the link could otherwise tick a confirmation, so none can be ticked from it. Operators should run QC sessions on a machine or account that holds nothing valuable.

## 6. Data model and verb contracts

Exit codes follow `Core.ps1`: 0 ok, 2 usage, 10 gate refused, 11 stale, 12 not found, 20 retryable, 21 accepted/pending, 30 config/secret, 40 claim held. HTTP mapping of `/api/v1/verbs` as in `Program.cs`: 0 -> 200, 21 -> 202, 2 -> 400, 12 -> 404, 10/11/40 -> 409, 20 -> 503, 30 -> 500 (Program.cs:124). The `/qc/*` handlers do not use it; they use their own reason-code table: `bad-link` 403, `link-expired` 410, `stale-head` 410, `rate-limited` 429, `no-such-pr` 404, `not-eligible` and `trust-confirm-needed` 409, `waiting-for-worker` 202, `started`/`existing` 200.

| Verb | Caller | Args | Exit and reason codes |
|---|---|---|---|
| `qc-sync` | sweep (admin) | none (part of `sync-board`) | 0; 20 `github-unavailable`. Offers and tears down only; creates no record |
| `qc-link` | admin, `qc-sync` | `item`, `pr` | 0 `posted`/`edited`; 10 `not-eligible` (with `reasons[]`); 30 `public-url-not-reachable`, `no-token-secret` |
| `qc-view` | page (token) | `pr`, `token` | 0; 30 `bad-link`; 11 `stale-head`, `link-expired`; 12 `no-such-pr` |
| `qc-request` (Start) | page or admin | `pr`, `token`, `nonce`, `from`, `confirm`? (admin only) | 0 `started`/`existing`; 10 `not-eligible`, `trust-confirm-needed`; 11 `stale-head`; 21 `waiting-for-worker`; 20 `rate-limited` |
| `qc-reset` | page or admin | `pr`, `sha` (optional, defaults to current head), `from` | 0 `reset`; 11 `stale-head` (when `sha` given and differs); 10 `not-eligible`; 12 `no-environment` |
| `qc-teardown` | page, admin or sweep | `pr`, `reason` | 0 `torn-down`/`already`; 21 `waiting-for-worker-stop` (worker offline; records `torn-down` after the lease expires) |
| `qc-reassign` | admin | `pr`, `worker` | 0; 10 `worker-unqualified`, `worker-full`; 12 `no-such-worker` |
| `qc-list` | admin | `include` (`all`/`active`) | 0 |
| `qc-touch` | page | `pr`, `token` | 0 |
| `qc-job` | `qc` token | `item`, `pr` | 0 job facts; 10 `qc-trust-refused` (reasons), `fork-pr`, `wrong-state`; 11 `stale-head`; 12 `not-found` |
| `qc-progress` | `qc` token | `item`, `pr`, `state` (building/running), `log-tail-file`? | 0; 10 `bad-transition`; 11 `stale-assignment`; 40 `claim-held` (not your assignment) |
| `qc-report` | `qc` token | `item`, `pr`, `sha`, `env-id`, `url`, `port`, `local-health` | 0 `ready` (`probe` verified or unverified); 20 `unreachable` (probe connected, bad answer, or no local health); 10 `loopback-url`, `url-host-not-allowed`, `bad-transition`; 11 `stale-head` |
| `qc-fail` | `qc` token | `item`, `pr`, `code`, `reason`, `log-tail-file`? | 0; codes accepted: `build-failed`, `start-failed`, `health-timeout`, `no-reachable-url`, `unreachable-url`, `no-dotnet`, `port-busy`, `no-memory`, `profile-incomplete`, `trust-refused`, `app-down` |
| `qc-heartbeat` | `qc` token | `item`, `env-id`, `mem_free_mb`, `app_alive`, `local_health` | 0 with `action` = `continue`/`teardown`/`reset`/`re-report`; 11 `stale-assignment` |
| `qc-stopped` | `qc` token | `item`, `env-id` | 0; 12 `no-environment` |
| `merge` (changed) | owner | existing | adds 10 `qc-approval-missing`, `qc-not-run` for peer-approved non-auto items |

Auth: `QcVerbs = { get-item, accept, qc-job, qc-progress, qc-report, qc-fail, qc-heartbeat, qc-stopped }` for role `qc`. `release` is not in it and `qc-teardown-ack` does not exist (the worker confirms with `qc-stopped`). `AuthorizeVerb` (Auth.cs:83) sets `kind = "own-item"` for every role except inspector, and `Plant.OnVerb` `accept` (Plant.cs:196) would then make the QC worker the owner while `release` (Plant.cs:200) would clear the owner's assignments; so role `qc` gets an explicit branch with `kind = "qc-env"`, recorded in `qcOf`. The token's item must equal the call's item and its `assignment` must equal the record's assignment; `holder` is overwritten from the credential. Page verbs run under principal `Kind = "qc-click"`, an explicit `AuthorizeVerb` branch that allows only `qc-view`, `qc-request`, `qc-reset`, `qc-teardown`, `qc-touch`, carries the capability token and client address, no identity, and is not callable through `/api/v1/verbs`.

New events:

| Stream | Event | Data |
|---|---|---|
| owner (item mailbox) | `qc.requested`, `qc.ready`, `qc.failed`, `qc.torn_down`, `qc.approved`, `qc.stale` | `pr`, `sha`, `state`, `reason` (no URL in owner events; the owner reads it with `get-item`) |
| worker (directed) | `item.assigned` (job `qc-env`), `qc.reset`, `qc.teardown` | `item`, `pr`, `sha`, `env_id`, `assignment`, `mode` |
| firehose (`/api/v1/events`) | the same names | metadata only |
| webhook-derived | `pr.opened`, `pr.head_changed`, `pr.closed`, `pr.merged`, `pr.drafted`, `pr.reviewed` | `pr`, `sha`, `login`, `state` |

The owner session uses `qc.requested`, `qc.ready`, `qc.failed`, `qc.torn_down` and `qc.stale` only to inform the person in its summary. `qc.approved` (and `qc.ready` when an approval for the head exists) is the trigger to retry `merge`: under `peer-approved`, `merge` refuses `qc-approval-missing` and `qc-not-run` (10), and the owner (skills factory-follow-through and functional-testing) treats an exit 10 `qc-*` as "wait for that event", not park. It does not call QC verbs.

## 8. Failure modes and edge cases

| # | Case | Handling |
|---|---|---|
| 1 | Worker disconnects mid-build | Lease (in memory; `leaseMinutes` 30 shortened to `timing.qcLeaseMinutes` 5 for QC) expires; record to `assigned(relaunch)` on another worker; `maxRelaunches` then `failed(no-worker)`; the old worker, on return, finds a stale assignment (11) and runs `stop` on its own leftovers; a startup sweep on the worker removes `qc/*` dirs with no live assignment |
| 2 | Two people click | Idempotent (section 2.3); both see the same status |
| 3 | PR force-pushed or new commit | `synchronize` -> head changed; the offer comment gets the new link; the old environment is marked `stale` and torn down after `timing.qcGraceMinutes` (30) unless the person resets first; nothing rebuilds by itself; stale approvals not counted |
| 4 | PR closed or merged | Immediate teardown; page shows "closed" |
| 5 | App dies, tunnel dies, or the worker sleeps | Heartbeat `app_alive:false`, or three failed probes of a verified URL: `failed(app-down)`; the page shows the failure and a Reset button; no automatic reset; laptop sleep appears as lease loss (case 1) |
| 6 | Port clash | `run` picks the next free port in the range, three tries; then `qc-fail port-busy` and the person may reassign |
| 7 | Build fails | `failed(build-failed)` with the last 30 log lines (redacted) on the page and in one journal line; the owner receives `qc.failed`; Reset is the way forward; repeated failures do not loop (one build per Start or Reset) |
| 8 | No worker connected / none qualifies | State stays `requested`; page says why ("no connected worker has a QC profile with the .NET SDK"); `qc-waiting` journal; the dashboard row shows it; the request is served when a qualified worker connects (it is the person's earlier Start, not a new automatic one) |
| 9 | Worker profile lacks the .NET SDK | Not selected (no `dotnet` capability); if selected by a stale registration, `prepare` runs `dotnet --version`, `qc-fail no-dotnet` and the plant manager excludes that worker for this PR |
| 10 | `Auto Merge` label added later | Item becomes auto: record torn down (`label-changed`), offer comment edited to "no longer needs QC", the existing `merge` path applies; removal of the label later makes the PR `available` again. A human approval already given stays on GitHub but QC state is not revived |
| 11 | Gateway restart | Records rebuild from state comments and Plant `PlaceQc`; workers resume by `my-items` including `qc-env` jobs. What is rebuilt, what is lost and the `re-report` recovery are in 3.1 |
| 12 | Out of memory on the worker | App killed; heartbeat reports `app_alive:false`; `failed(no-memory)`; worker `qcCapacity` is lowered for 30 minutes |
| 13 | The inspector escalates while QC is running | Independent. One human approval of the head clears the hold and satisfies QC if the environment ran |
| 14 | Person never starts or never tests | `available` costs nothing; the link expires. A `ready` environment hits idle teardown |
| 15 | Offer comment deleted by someone | Next sweep re-posts (marker missing) |

## 10. Decisions and open questions

### Decided 2026-10-11
1. Click identity. Decision text: "Anyone can click. But people not on same subnet won't be able to reach it because the ai session will be running on a user computer and not in azure." Applied: no identity check on the link (sections 1, 2, 3.3, 6); capability token kept; reachability is by network and stated on the page and comment; the approval of the PR stays a `humanApprovers` GitHub review.
2. Sandbox. Decision text: "Sandbox can be whatever environment the session is running in. Each session environment prompt can set up environment for app based on architecture of the app." Applied: no sandbox levels or gating; per-session QC environment profile in the connect prompt (section 4.2); hygiene kept as defaults (4.4).
3. Start on request. Decision text: "Qc environment only starts on user request." Applied: sweep never creates or assigns a job and never rebuilds; no `qc.followHead`; no automatic reset; the comment and dashboard only offer; automatic teardown stays because it only stops things (3.5).

### Open (recommendation first)
1. Must the human approval be required to merge non-auto items under `peer-approved`, and must a QC run have happened? Recommended: yes to both (`qc-approval-missing`, `qc-not-run`), docs-only items exempt. Anyone may start the run, so `qc-not-run` only asks that some environment for that SHA reached `ready`; the approval itself must come from `humanApprovers`. Otherwise QC is decoration; the gate costs one extra refusal code and the person already has to approve.
2. What should the profile do when the machine has no address others can reach (public tunnel question)? Recommended: `address: none`, so the worker reports `no-reachable-url` and the page says no reachable worker is available; a tunnel command is used only if the operator wrote one into that session's profile, and the page then warns that the URL may be public to anyone holding it. Default is no tunnel, because the app runs untrusted code and the click is open to anyone; reachability by network is the access control.
3. Which PR authors are trusted to be run without an extra operator confirmation? Recommended: the factory App logins and the people in `humanApprovers`; other write-access collaborators need the operator confirmation on the dashboard; forks never. This keeps the common case one click and puts friction on the unusual case.
4. SQLite or SQL Server for the environment's database? Recommended: SQLite in `E/data/` as the profile default if step 0 confirms the Server runs on it; a profile may name a local SQL Server database instead. A file database makes reset and teardown trivial (delete a directory) and needs no daemon; a shared SQL Server instance is a data-leak and name-clash risk.
5. Should a worker's QC capacity be shared with its owner capacity? Recommended: no, separate counters (`qcCapacity` from the profile, default 1) plus the free-memory check. An owner session mostly waits, while a QC build uses real CPU and memory; the separate counter lets an owner keep working while one environment runs, and the memory check stops overload on the 12 GB box.
