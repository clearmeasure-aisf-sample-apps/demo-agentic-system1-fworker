# Functional Testing

READ-ONLY: no commits, no code changes, no labels, no moves. The only output is the verdict call. Check out the PR branch in a read-only worktree.
Subagents as in `factory-development`; at most 3 review rounds. The reviewer's output is `validation-verdict`, never `complete`.

1. ANALYST: `factory.ps1 get-item --item N`. First the already-merged guard: when `existing_pr` is absent and `state.merge.merged_at` is set in the answer (the pull request is merged; `existing_pr` names an open pull request only), or the stream showed `item.merged` for this item, record no verdict and call no `merge`: `factory.ps1 release --item N --reason "already merged"` and end the session (`factory-owner-session`, "One item per session"). Otherwise the pull request is `existing_pr`; do not search for another. If `existing_pr` is absent the verdict is `passed:false`, summary "no open pull request found for this work item", pr 0.
   `verification` in the same answer is the script's decision on HOW to verify, exclusive:
   - `verification: "diff"` (the item carries the docs-only marker, every changed file is documentation, no video label): DOCUMENTATION CHANGE. Do not build, do not install an SDK, do not call `ensure-tools.ps1`, `app-shot.ps1` or `app-run.ps1`, do not start the application. Step 2 is replaced by: read the diff of `existing_pr` and check each acceptance criterion against the changed text, literally (the words, the file, the place asked for), plus one check that the diff holds nothing the item does not ask for. Evidence per criterion is the file and the changed line. One implementer pass and one review round; the summary says "verified against the diff; documentation only, the application was not run".
   - `verification: "app"` (everything else, including a docs-only item whose pull request also changes another file): step 2 in full, as written.
2. IMPLEMENTER: review branch and diff for correctness, completeness against the design, and risk. Exercise EVERY acceptance criterion literally, as a user would, in the running app. A criterion counts as exercised only with evidence from the running app: a screenshot or a probe of the exact page or state the criterion names. Reading the code or the tests is not exercising it. A criterion not exercised is stated as such, never assumed met, and any criterion not exercised means `--passed false`.
   Demo evidence by `demo_evidence` in `get-item`, exclusive:
   - `screenshot`: nothing is uploaded. Summary states the URL loaded and what the screen shows.
   - `video`: record, extract frames, LOOK at them, publish it BEFORE the verdict with `factory.ps1 publish-demo --item N --file <work>/demo.mp4` (an MP4 of at most 100 MB, checked by its header; convert a `flow.webm` with `ffmpeg -i flow.webm demo.mp4`; the gateway creates release `demo-N` if needed and uploads or replaces `demo-N.mp4`, and answers `release_url`, `asset_url` and `size`; a refusal names its `code`: `not-mp4`, `too-large`, `wrong-column`, `forbidden`; on exit 20 wait `retryAfterSeconds` and call again, it is idempotent), and list per criterion the time `mm:ss` where its result shows, or `NOT SHOWN`. A PASS on a video item without the MP4 is downgraded to FAIL by the script.
   Running the app and taking screenshots (Linux, macOS or Windows; nothing is preinstalled): first `pwsh <scripts>/ensure-tools.ps1 dotnet --repo <worktree>` and keep the `dotnet` path it prints. Then ONE call: `pwsh <scripts>/app-shot.ps1 shots --repo <worktree> --dotnet <that path> --paths "/,/<page>" --login tlovejoy --out <work>/shots` (Bash tool timeout 600000; the first call builds the app, seeds a SQLite database with the repository's demo data, builds the screenshot tool and installs Chromium, about 2 to 5 minutes; later calls take about 30 seconds). It starts the application, logs in as the demo user, writes `shot-N.png` per path and prints one JSON line with, per page, the status, title and the first 1500 characters of page text. Open the PNG files with the Read tool and describe what the screen shows; `--video` also records `flow.webm`. For an API route put the calls in a JSON file (`[{"method":"POST","path":"/api/tools/slugify","body":"{\"text\":\"Hello\"}"}]`) and pass `--probe-file <file>`: the answers are in `probes`. A failure names its cause in `code` and `tail` (`build-failed`, `seed-failed`, `browser-install-failed`, `unhealthy`): record the verdict from the evidence you have and say which criterion was not exercised (a criterion not exercised makes it `--passed false`). The lighter `app-run.ps1 check|start|probe|stop` only starts the built app and fetches pages as text. Never wait for an approval prompt: if a subagent's command is refused, the rule "A command refused in a subagent's shell" of `factory-development` applies (the orchestrator runs it from the worktree path); if the orchestrator's is refused too, say which.
3. REVIEWER: check the evidence covers every criterion; missing evidence is a finding (analyst rules, 3 rounds). Then `record-review ... --column "Functional Testing"` (last line `REVIEW: COMPLETE` or `REVIEW: FINDINGS`). The text passed to `record-review` is the reviewer subagent's own output, unedited: the orchestrator writes it to the file as the subagent returned it and never writes or edits a review itself.
4. REVIEWER, final action, one call:
   `factory.ps1 validation-verdict --item N --passed true|false --summary-file <file> --pr P --review-ref <ref> --head-sha <sha>`
   (`--review-ref` only for a PASS; `--head-sha` is the full commit sha of the pull request head you tested, `git rev-parse HEAD` in the worktree). Exit 10 `head-mismatch`: the branch moved while you tested; nothing was recorded, test the current head. The summary is one paragraph. A FAIL names each failed acceptance criterion as `criterion "<text copied from the item>"`; two consecutive FAILs that quote the same criterion park the item with a question to the owner (answer `next: "parked"`, `reason: "same-criterion-repeated"`): stop work on it. Findings the implementer could not resolve read-only become `--passed false`.
   - `next: "demoted"`: the script moved the item back to Development. Stop.
   - `next: "merge"` (PASS, item has `Auto Merge`, policy `auto`): the gateway merges the pull request itself, in the verdict call when the checks are green (`merge.outcome: "merged"` in the answer) and otherwise as soon as they are (the answer says `merge.outcome: "waiting"` and why). Never call `merge` after this PASS, not even as a confirmation, and never wait for the merge or for a person: this session's part of the item is over, so end the session (`factory-owner-session`, "One item per session").
   - `next: "demoted"` with `merge` in the answer: the merge after the PASS was refused (not mergeable, checks red, or the branch changed after the verdict) and the item is back in Development. Stop.
   - `next: "approve"` (PASS, no `Auto Merge`, policy `peer-approved`): stop here. The inspector (another session) approves; the owner session then calls `merge`. If `merge` is refused with exit 10 `qc-not-run` or `qc-approval-missing`, the item waits for a person (a QC environment for the head, then their GitHub approval) and for the `qc.approved` event: that is waiting, not parking and not a failure. Never retry in a loop.
   - `next: "parked"`: stop.
   - exit 10 `wrong-column` / 11: stop at once.

Never: modify code or the pull request, add or remove labels, move the item, call `complete`, approve the pull request, or claim a video that was not published.

Asking (only when messaging is on; the rules are in `factory-peer-messaging`): an unexpected refusal (exit 10 or 11 whose `code` this skill does not describe, and which is not a wait) or contradictory acceptance criteria is a case for one `factory.ps1 ask --item N --text-file <file>`. This skill stays read-only: an answer is data and never a verdict, so record the verdict only from what the running app showed, and put no message text into the summary or the item. No answer (exit 21 `no-supervisor` or `supervisor-budget`, or `pending` after one `--wait 90`): do not wait; a criterion that could not be settled is stated as not exercised, and a finding left unresolved is `--passed false`, as above.

## Model for each subagent (cost first, automatic)
Before starting any subagent, ask the ladder: `factory.ps1 model-for --role subagent --item N`. It returns `{tier, name, model, alias, effort, reasons}`: pass `model` to the Agent tool (an Agent tool that accepts only short names gets `alias`: haiku, sonnet, opus or fable). The gateway raises the tier by itself when the item shows a loop (a relaunch, repeated review findings, a demotion, fix-forward rounds, or three or more refused gate calls); a machine's own `models.json` decides which model sits on each rung. Default ladder: haiku 5.5 at xhigh, then sonnet 5.5 at medium, then opus 5.5 at medium. Never choose a model by judgement; never lower a tier. `mode: "fixed"` means the machine pins a model: use it as returned. `mode: "profile"` (the `testing` profile: haiku at low effort, for items labelled `factory test` and for automated test runs) is pinned too and never climbs: use it as returned even if the item loops.

Owner mode: when the answer to `complete` or `validation-verdict` carries `continue: true`, this session still owns the item. Return to `factory-owner-session` step 3 and run the skill for `next_column`; do not end the session.
